# Design

## Context

См. proposal.md. Schedule на C уже собирает группы и `milestoneAttachments` без смены DTO: веха каталога остаётся одной строкой, меняются `parentKey`, `wbs` и `siblingOrder`. `links` сегодня — только `work:<id>` и обязательный type. Раскрытие по умолчанию — `project_group:AN-08` и `stage_group:8.2`. Агент №2 в том же репозитории пишет change `schedule-work-actual` и черновики UX и ADR-0004 про факт. Эти файлы дерево не требует.

## Goals / Non-Goals

**Goals:**

- Зафиксировать два требования отдельно и применить дерево, не дожидаясь стрелки.
- Описать контракт `kind` так, чтобы work↔work не потерял FS/SS/FF/SF, а milestone→work не получил выдуманный тип.
- Один писатель на `schedule-works.ts`.

**Non-Goals:**

- Фактические интервалы, вторая полоса факта, лаборатория C08.
- Правка комплекта показа и общего плана.
- Импорт остальных проектов аналитика и расчёт сети.

## Decisions

1. **Дерево только в fixtures снимка C.** Новые группы и работы используют уже существующие поля. `MS-UTL-PWR` добавляется второй записью `milestoneAttachments`, не новой вехой каталога. Даты вехи остаются baseline `2027-02-18` и прогноз C `2027-04-15`.
2. **Порядок корней.** `siblingOrder`: `AN-08` = 0, `AN-24` = 1, `AN-09` = 2. Питание стоит перед HVAC, эпизод панелей остаётся первым. Новые корни не добавляются в набор раскрытия по умолчанию.
3. **Синтетика дат работ.** В исходнике дат нет. Интервалы подобраны к `asOf` C `2027-03-01`: Delayed и OnSchedule пересекают эту дату, Waiting `9.3.2` начинается на следующий день после прогноза вехи питания. Это допущение показа, не лаг сети. Прогресс не заполняется.
4. **Стрелка — другой вид записи, не пятый type.** После review DTO различает `kind`:
   - `scheduling`: `sourceRef` и `targetRef` вида `work:<id>`, `type` обязателен.
   - `cross_project_predecessor`: `sourceRef` = `milestone:MS-UTL-PWR`, `targetRef` = `work:9.3.2`, поля `type` нет. Id связи `LNK-X-PWR-HVAC`.
   Альтернатива «записать FS и оставить work↔work» отклонена: она подменяет веху или выводит тип из знака `⇢`.
5. **Отрисовка не является типом.** Адаптер крепит линию к ромбу и к началу прогнозной полосы приёмника. Подпись: «Межпроектное предшествование, тип не указан». Технический код геометрии DHTMLX живёт только в адаптере. Линия попадает в диаграмму только если оба конца есть среди видимых строк. Скрытый предок или фильтр убирает линию. В режиме факта цель без факта оставляет прогнозную полосу, и линия остаётся на ней. Закрытый факт, который убирает прогнозную полосу цели, скрывает линию в этом режиме.
6. **Порядок общих файлов.** Поля C07 в `schedule-works.ts` записаны до `LNK-X-PWR-HVAC`. Стрелка добавлена поверх них и поля факта не переписывает. После проверки Агент №3 эти общие файлы освобождает. C07, адаптивность и комплект показа остаются у своих владельцев.

## Risks / Trade-offs

- [Два change меняют один capability `schedule-workspace`] → дельты аддитивные; дерево не модифицирует требования иерархии AN-08.
- [Номер строки WK-01 сдвинется] → комплект показа ищет WK-01 по имени; тексты показа не правим.
- [Сводная полоса новых групп появится из дат детей] → это уже правило групп, отдельные даты группам не задаются.
- [До review стрелки директор видел две свёрнутые ветки без линии] → после принятого review линия есть и видна только при обоих раскрытых концах.

## Migration Plan

1. Документы и OpenSpec.
2. Fixtures и проверки дерева. Откат — удалить новые группы, работы и attachment `MS-UTL-PWR` из снимка C.
3. После review стрелки — DTO, валидация, адаптер, браузер. Этот шаг выполнен 2026-11-06. Откат — не отдавать `LNK-X-PWR-HVAC`; четыре связи WK остаются.
