## Готовность к показу

- **Группа 1 — продуктовый стоп по ближайшему показу.** Известного дефекта продукта, который блокирует запуск демо или маршрут «портфель → программа → проект» и снимки C → D → F, нет. На иерархической «Временной шкале» снимка C прогнозная полоса остаётся основной; базовая рисуется над ней только у работы с обоими концами интервала.

- **Группа 2 — оставшийся шлюз репетиции (не дефект UI, не блокер кода).** **E02** — пункт остаётся открытым, пока другой участник не проведёт репетицию по сценарию и расхождения не будут записаны в [walkthrough](../03-product/demo-v1-acceptance-walkthrough.md) (раздел «Репетиция (E02)»).

- **Группа 3 — открыты после показа или вне доводки демо, не стоп-шоу.** **C06**, **C07**, **F07**: по C06 вертикали `vis-minor` — месячные границы, их скрытие ухудшает чтение ([отчёт](reports/2026-11-06-c06-vis-month-grid.md)); по C07 полоса факта ждёт макета ОСУП; базовая полоса над прогнозом на иерархической шкале включена отдельно (H04) и фактом не является, лаборатория **C08** остаётся проверкой Community и не переносит split в продукт ([отчёт](reports/2026-11-06-c08-gantt-interval-lab.md)); по F07 кнопка collapse над сайдбаром на 2026-11-06 не воспроизведена ([отчёт](reports/2026-11-06-f07-g12-shell.md)). **C05** и платформенная часть **E04** (хлебные крошки в `reference platform`; крошки демо не менялись) остаются вне активной доводки демо, чекбоксы пустые.

## 1. Состав портфеля и демоданные

Сверить с Олегом иерархию «портфель → программы → проекты → работы». Портфель отражает создание завода целиком. Стройка, ИТ, оборудование, организационные работы и подбор персонала обсуждались как примеры группировки. Для показа подготовить правдоподобные проекты, контрольные точки и связанные проблемы, например задержку панелей чистых помещений. Результат — один согласованный набор данных для обзора, графика, состава программы и карточки проекта. Источник — 00:14:51–00:16:18.

## 2. Терминология

В обзоре использовать «Состояние по программам» вместо «Готовность направлений». В навигации развести «Программы» и «Проекты». На графике писать «Вехи портфеля» или «Вехи программы» по контексту. Для проекта использовать «Контрольные точки» либо «Вехи». Заголовок блока решений — «Требуется решение». Принятые решения остаются доступны в этом блоке с явной отметкой о принятии. Для рамки с исключениями выбрать понятную формулировку по содержимому, например «Требует внимания» или «Проблемы и риски». Убрать повторяющие цвет статуса слова. Источник — 00:00:00–00:01:18, 00:02:41–00:04:08, 00:13:31–00:14:51.

## 3. Обзор портфеля

Сохранить компактный обзор из трёх блоков. Показатели состояния и дата запуска относятся ко всему портфелю, справа показано состояние программ. По умолчанию график показывает немного укрупнённых вех портфеля. При выборе программы он показывает её вехи с большей детализацией, а рядом доступно действие «Перейти к программе». Детализацию задаёт атрибут уровня вехи. При снятии выбора график возвращается к портфелю. Источник — 00:00:00–00:01:18, 00:04:31–00:05:26.

## 4. Временная шкала и снимки

Воспроизвести смещение пунктирного маркера даты, замеченное около 28 февраля. Проверить его привязку к выбранной дате на всём диапазоне, включая крайние снимки. Проверить семантические уведомления при смене снимка и возможность их отключить. В демо проверить сравнение снимков. Правило выбора даты сравнения для реального продукта осталось открытым. Неделя к неделе и месяц к месяцу прозвучали как примеры. Источник — 00:01:38–00:02:41, 00:04:14–00:04:31.

**Статус 2026-11-06, вечер:** C05 остаётся гипотезой в [дашборде](../05-ux-ui/demo-v1-dashboard.md): база по умолчанию — предыдущий снимок, явная подпись «Сравнение с: …», пустой период не подменяется. ## 5. Дашборд программы

## 15. Интервальные работы и стрелки на странице «График»

В DHTMLX Gantt Community обычная работа задаётся как `type: task` с началом и окончанием либо длительностью. Библиотека рассчитывает ширину полосы из интервала. Для семантического цвета адаптер может назначать CSS-класс через `task_class` по статусу из данных. Согласовать соответствие статусов токенам и проверить короткие полосы на рабочем масштабе.

DHTMLX поддерживает четыре вида связей через `source`, `target` и `type`. Адаптер сопоставляет доменные типы с `gantt.config.links`: SS — начало–начало, SF — начало–конец, FF — конец–конец, FS — конец–начало. В демо достаточно отображения стрелок. Правила пересчёта графика остаются отдельным вопросом.

Текущий Schedule передаёт вехи и поставки как точечные строки, а адаптер получает пустой список связей. Для работ нужны согласованные интервалы. Разность базовой и прогнозной дат вехи обозначает отклонение в днях. В исходнике аналитика стрелки различают внутри- и межпроектные зависимости, поэтому типы SS, SF, FF и FS нужно уточнить отдельно.

**Демо-контракт G07–G11 согласован 2026-11-06** (прогноз, inclusive end, календарные дни, authored-статусы, work↔work, `work:<id>`). Docs: [DOC-UX-005](../05-ux-ui/demo-v1-schedule-workspace.md), [ADR-0004](../06-architecture/decisions/0004-d12-dhtmlx-gantt-community.md), [OpenSpec](../../openspec/changes/demo-v1-schedule-work-bars-links/proposal.md). До кода остаётся curated подвыборка: [запрос аналитику](reports/2026-11-06-g07-g11-analyst-questions.md). После ответа — параллельно API+fixtures и FE.

4. **Перед отметкой чекбокса** проверить согласованность документации, реализации и критериев приёмки. Для OpenSpec пройти оставшиеся этапы workflow, включая архивирование и обновление living specs по правилам репозитория. В результате работы указать ID задач, обновлённые документы, проверки и открытые вопросы. При передаче работы оформить handoff по правилам репозитория.

| Уровень | Когда обновлять и где смотреть |
| --- | --- |
| Продукт и сценарий | При изменении маршрута руководителя, состава демо или условий показа. Начать с [сценария приёмки](../03-product/demo-v1-acceptance-walkthrough.md) и связанных product-документов. |
| UX и навигация | При изменении подписи, компоновки, переходов или состояний. Для B10–B11 и C09–C11 смотреть [спецификацию дашборда](../05-ux-ui/demo-v1-dashboard.md), для F01–F06 — [спецификацию оболочки](../05-ux-ui/demo-v1-shell-navigation.md), для G07–G11 — [спецификацию графика](../05-ux-ui/demo-v1-schedule-workspace.md). |
| Поведение и API | При изменении действующего пользовательского поведения или контракта данных. Сверить [living specs](../../openspec/specs/README.md) и подготовить изменение в `openspec/changes/`. Для G07–G11 описать форму интервалов, типы зависимостей и правила отображения. |
| Архитектура и эксплуатация | При смене принятого решения о рендерере или границах адаптера сверить [ADR-0004](../06-architecture/decisions/0004-d12-dhtmlx-gantt-community.md). При смене URL документации обновить [гайд локального запуска](../10-operations/local-dev-and-demo.md) и связанные документы по прокси и развёртыванию. |
| Демоданные | При изменении fixtures сверить [сценарий данных](../03-product/demo-v1-mock-narrative-data.md). Зафиксировать источник, правила сопоставления, снимки и значения, которые согласованы специально для демо. |

## Границы плана

Обсуждение OpenSpec, Docusaurus, переноса Wiki и общей базы знаний относится к отдельному потоку работ команды. В плане приложения остаются работы по сценарию показа и решения о переносе на платформу. Порядок групп предложен для обсуждения командой. Статус выполнения задач и сроки сверяются с текущей сборкой и командой.
